# Sai Group inventory

Replaces the `Sai_Heat_Sock_Management.xlsx` workbook (STOCK IN / STOCK OUT /
STOCK SUMMURY) with a web app the store team can open from anywhere — desktop
in the office, phone or tablet on the shop floor.

What it fixes, versus the workbook:

- **Every product has a permanent ID** (`SAI-BURNR-01`), and every countable
  unit its own (`SAI-BURNR-01-001`), generated by the database.
- **Where each unit is** — in the store, out at a named job, damaged or missing.
- **Jobs keep their history**, even after every unit has come back.
- **Stock value per unit**, because the same product bought from different
  makers costs different amounts.
- **One ledger, not three sheets.** The balance is always the sum of the history.

## Setup

### 1. Create the Supabase project

Create a new project at [supabase.com/dashboard](https://supabase.com/dashboard)
(free plan, region South Asia (Mumbai)). On the create-project screen:

- **Enable Data API** — leave **checked**. `supabase-js` needs it.
- **Automatically expose new tables** — **uncheck** it. `schema.sql` grants
  exactly what the app needs and nothing else.
- **Enable automatic RLS** — **check** it.

### 2. Run the SQL files

In **SQL Editor → New query**, paste and run each file once, in this order:

| File | What it does |
|---|---|
| [`supabase/drop-all.sql`](supabase/drop-all.sql) | Only on a project that already ran an older `schema.sql` and you're starting over: wipes every table, function and trigger this app created, so `schema.sql` can run clean. **Deletes all data with no way back** — skip it on a brand-new project. |
| [`supabase/schema.sql`](supabase/schema.sql) | Creates every table, function, grant and policy. |
| [`supabase/data.sql`](supabase/data.sql) | Loads the 12 starting categories, the 56 product names from the workbook, and the 7 job names. Every product starts at 0 — enter real opening stock, thresholds and costs yourself. Run it only once. |

### 3. Create your login

**Authentication → Users → Add user**, with a password. **The first account
becomes the admin**; everyone after starts as a viewer and is promoted from the
app's *Manage people* screen. Then under **Authentication → Sign In /
Providers**, turn **off** public sign-ups.

### 4. Point the app at it

Copy `.env.local.example` to `.env.local` and fill in the project URL
(**Project Settings → Data API**) and the publishable / `anon` key
(**API Keys**):

```
NEXT_PUBLIC_SUPABASE_URL=https://xxxxxxxx.supabase.co
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=....
```

Never put the `service_role` / secret key in a `NEXT_PUBLIC_` variable.

### 5. Run it

```bash
npm install
npm run dev     # http://localhost:3000
```

### 6. Deploy

**Without git — upload this folder.** Vercel's website can only import a git
repository, but its command line uploads whatever is in the folder you run it
from, so there is nothing to set up first:

```bash
npx vercel login
npx vercel link                                    # name the project
npx vercel env add NEXT_PUBLIC_SUPABASE_URL
npx vercel env add NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY
npx vercel --prod
```

`env add` asks for the value in the terminal, and which environments it is for —
pick all three. Set both **before** the first `--prod` build: `NEXT_PUBLIC_*`
values are baked into the JavaScript when it is built, not read when the page
loads, so a build that ran without them keeps saying the app is not configured
until you build again.

The upload follows `.gitignore`, so `.env.local`, `node_modules` and `.next`
stay on your machine. Every later change is one command: `npx vercel --prod`.

**With git**, push to GitHub and import at [vercel.com/new](https://vercel.com/new),
adding the same two variables there. Vercel then rebuilds on every push, and you
get a history and a way back when a change breaks something.

Either way, finish in Supabase: **Authentication → URL Configuration**, set
**Site URL** to the Vercel address and add it under **Redirect URLs**, so
password-reset and invitation links come back to the app instead of
`localhost`.

## The pages

| Page | What it answers |
|---|---|
| **Dashboard** (`/`) | Stock health, the reorder queue, recent movements with their job. Total stock value for admins. |
| **Inventory** (`/inventory`) | What we have. Search, category chips, status filter and sort — all kept in the URL. CSV export. |
| **Product** (`/inventory/<id>`) | One product: its units with maker, year and whereabouts, and its history. Costs and value for admins. Edit or archive. |
| **Unit** (`/units/<id>`) | One physical piece: what it is, where it is, who made it and when, and everything ever recorded against it. |
| **Add item** (`/add`) | Creates the product and logs its opening stock. |
| **Update stock** (`/update`) | Receive (bought, built in-house, or returned from a job), Dispatch to a job, Adjust after a shelf count or to fix an earlier entry, or Damage / loss (damaged, missing, scrapped, repaired, found — in the store or out at a job — or cable/coil used up at a job). Every entry can carry a note. |
| **Jobs** (`/jobs`) | Each job's units currently out, and everything that ever went to it. Add, edit, close or reopen a job; delete one only if nothing has ever been sent to it. |
| **History** (`/history`) | Every movement, filterable by type, date, reason, category and job. CSV export. |
| **Manage people** (`/admin`) | Admins only. Switch accounts between viewer and admin; review categories; back up and manage the size of the movement log. |

Viewers can see and export stock, but cannot change anything and cannot see
costs or stock value — the database only hands those to an admin, so they are
not in a viewer's API responses either.

**Find a unit by ID** sits in the account menu, top right: type the ID marked
on a piece of equipment (`SAI-BURNR-01-001`) to open that unit's page — which
product it is, where it is, who made it and in which year. A product ID or name lists
that product's units instead.

**Nothing is ever sold.** Stock leaves the store to go to a job and comes back;
there is no "sold" path anywhere in the app.

**A loss at a job is recorded once.** A unit at a site can be marked missing
without coming home first, and cable burnt or left behind is written off against
that job. Neither touches the store balance — the store gave the stock up when
it was issued — so the same loss is never counted twice.

**Cable that gets installed is not a loss.** "Used at Job" closes out what a
job still has out the same way a loss does — the store balance already gave
the amount up at dispatch — but says honestly that it did its job, instead of
recording ordinary use as Damaged, Missing or Scrapped.

## ID scheme

```
SAI-<CATEGORY CODE>-<2-digit sequence>      product
SAI-<CATEGORY CODE>-<2-digit sequence>-<nnn> one physical unit of it
```

`data.sql` seeds 12 starting categories (`BRN` Burners, `BLW` Blowers, `CPL`
Control panels, `PMP` Pumps, `HOS` Hoses, `AIR` Air distribution, `TCS`
Thermocouples & sensors, `INS` Recorders & instruments, `PWH` PWHT panels,
`CBL` Cables, `HTE` Heating elements, `MSC` Storage & misc). Admins can add
more from **Add item** or **Manage people** — pick a name and a 3-letter code;
the code is fixed once set, since it's already baked into every item ID that
category has minted.

Products counted in `pcs` get one unit row per physical item. Products measured
in `m` or `kg` are tracked by amount only. A unit ID only means something on the
shop floor if it is labelled on the equipment.

## Data model

| Table | One row per |
|---|---|
| `items` | product — balance, reorder threshold, tracking mode, archived flag |
| `units` | physical unit — maker, year made, cost, status, current job |
| `movements` | stock event — signed quantity, reason, job, units covered, balance after, and the amount for a bulk write-off at a job (that entry's own quantity is always 0) |
| `jobs` | site or customer job |
| `job_stock` | cable/coil product at a job — how much went out there and hasn't come back (caps both returns and write-offs at that job) |
| `profiles` | login — display name and role |
| `categories` | product grouping — name and its fixed item-ID code |

Stock never changes with a plain UPDATE. `create_item` and `apply_movement`
change the balance and write the ledger entry in one transaction, and they are
the only way to do either.

**Valuation (admins only):** a countable product is worth the sum of the costs
of its units in the store; cable and coil use a weighted average cost. Units
with no cost are reported as "not priced", never counted as zero.

**Reorder alerts only where you set a minimum.** A product with no minimum
quantity never turns red — you own two of a burner, and an empty shelf usually
means both are out at jobs. Set minimums on what you actually restock (coil,
cable, spares) and those get the warnings; everything else reads "None in
store" in grey.

**Managing storage:** the free Supabase plan caps the database at 500 MB, and
the movement log is the only table that grows without bound. **Manage people**
shows how much of that is used and, once you've downloaded a backup, lets you
clear movements older than a date you choose (minimum 30 days back). Current
stock levels are unaffected either way — they live on `items` and `units`, not
on a sum of the log — so this only trims History, never a balance.

## Security

The role checks live in **Postgres, not in the browser**.

- **Signed out gets nothing** — `anon` has no privileges.
- **Nothing depends on a dashboard checkbox** — `schema.sql` revokes any
  default grants Supabase gives `anon`/`authenticated` before granting exactly
  what the app needs, so internal helpers like `mint_units` are never callable
  from the API.
- **Stock moves only through the logged path** — no INSERT on `movements`, no
  UPDATE on `items.quantity`, no UPDATE on a unit's status or job.
- **Costs are admin-only in the database, not just on screen** — `unit_cost` is
  left out of the SELECT grants on `items` and `units`, and handed back by
  `item_costs()`/`unit_costs()`, which return nothing to a viewer.
- **The ledger can't be edited or rewritten**, only ever appended to — with one
  exception: an admin can bulk-delete movements older than 30 days
  (`purge_movements`), to manage the free plan's 500 MB database cap. This
  never touches a balance or a unit's status, since those live on `items` and
  `units`, not on a sum of the log. Recent history is protected by the 30-day
  floor. Products can be archived but not deleted.
- **The write functions check the role themselves** (`assert_can_write()`),
  since they run as the table owner.
- **Attribution comes from the session**, not from the request.
- **No dynamic SQL**; the category code is validated before it is used in a regex.
- **CSV formula injection** is neutralised in exports (covered by tests).
- **search_path pinned** on every function.
